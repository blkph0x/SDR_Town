## Findings, ordered by repair priority

Evidence labels: **measured** = executable reproduction; **code-proven** =
reachable implementation contradicts its contract; **risk** = requires further
runtime validation; **gap** = explicitly absent capability.

### A01 / P1 - HF blanker can suppress a sustained stronger signal

**Measured.** `src/HfDemod.cpp:469-481` replaces high-amplitude samples with a
scaled previous sample but updates its magnitude estimator only for accepted
samples. A sustained level increase can therefore stay above the old threshold
indefinitely. This is not merely an AGC attack delay.

Continuous 1.5 kHz analytic USB tone at 192 kS/s, amplitude 0.01 for one second,
then 0.5 for two seconds: output RMS falls from 0.155 to 1.61e-8 by two seconds
and 8.58e-10 by three. A fresh decoder receiving the same strong tone gives
0.165 RMS. Both master and PR #32 reproduce it.

Repair: bounded impulse suppression with an estimator that can recover from a
sustained carrier/level change. Test noise-to-signal, weak-to-strong, isolated
impulses, clipping and recovery in AM/USB/LSB/CW. Do not tune AGC constants to
mask a stuck blanker.

### A02 / P1 - Live HF processing cannot keep up at common high IQ rates

**Measured, plus code-proven recovery problem.** `src/HfDemod.cpp:229-261`
recalculates the windowed-sinc kernel for each output; `:452-488` performs
per-input-sample oscillator transcendental operations. On this Ryzen 9 3900X,
MSVC /O2, isolated single-channel processing consumed:

| IQ rate | RF seconds | Master wall seconds | PR #32 wall seconds |
|---|---:|---:|---:|
| 2.048 MS/s | 0.9920 | 0.9081 | 0.1411 |
| 2.4 MS/s | 0.9967 | 1.0546 | 0.1504 |
| 10 MS/s | 0.9994 | 2.7065 | 0.2444 |

These are local diagnostic timings, not a universal hardware benchmark. At
2.4 and 10 MS/s master is already slower than real time before GUI/other work.
At 2.048 MS/s it leaves very little scheduling margin.

`src/MainWindowP25Orchestration.cpp:916-950` gives WFM/NFM bounded-lag IQ windows,
but HF uses `getNewSamplesForReceiver`. That wrapper at
`src/DeviceManager.cpp:2383` discards the discontinuity metadata. On overrun,
`:2336-2349` advances only to half a ring behind, supplies 256 artificial zero
samples and leaves HF unaware of the discontinuity. Half of the 2^25-sample
ring is still 8.192 seconds behind at 2.048 MS/s.

Repair: measured multirate channelization, cached/polyphase coefficients,
continuous oscillator state, and explicit IQ-window provenance/lag policy for
HF. Reset discontinuous state explicitly; do not play stale seconds of audio.
Keep the protected P25 path unchanged while adding the HF-specific contract.

### A03 / P1 - PR #32 improves speed but introduces severe HF alias leakage

**Measured; merge blocker.** The PR's fixed 95-tap coarse decimator is
insufficient for its largest decimation factors. At 10 MS/s, an equal-amplitude
193,807.7 Hz offset tone folds onto the 1.5 kHz wanted tone after coarse
decimation. Wanted/rejected RMS:

| Version | Wanted | Out-of-band test | Rejection |
|---|---:|---:|---:|
| Master | 0.163426 | 0.000001328 | about 102 dB |
| PR #32 | 0.163423 | 0.110438 | about 3.4 dB |

At 2.4 MS/s its 201.5 kHz blocker rejection is about 57.8 dB; that is a
different operating point, not evidence that the 10 MS/s path is safe.
Green CI currently misses the coarse-decimation folding frequencies.

Repair: split useful SSTV wiring from the DSP optimization; design multistage
anti-alias filtering against a documented passband/stopband requirement. Sweep
every folding band at every supported rate and test strong adjacent blockers,
partition invariance and CPU budget before merging.

### A04 / P1 - Satellite orbit prediction fails the independent SGP4 oracle

**Measured.** `src/Sgp4.cpp:129-267` was compared with Vallado/CelesTrak's
published satellite 00005 verification case. Position error is **1,633.895 km
at epoch** and **821.384 km at +360 minutes**; velocity errors are 0.97125 and
0.53267 km/s respectively. The current code nevertheless returns `ok=true`.
This invalidates reliable pass-time/elevation/Doppler claims for the predictor.

The implementation is not the complete reference algorithm. For example its
Kepler solve at `:214-233` treats argument-of-latitude as a scalar-eccentricity
Kepler equation, while the reference uses eccentricity components and periodic
corrections. Correcting one expression alone would not qualify the remainder.
The header also explicitly omits deep-space propagation without a matching
unsupported-orbit rejection at the interface.

Repair: adopt a pinned, license-reviewed complete SGP4 implementation behind
the existing interface, or prove the entire implementation against the official
vector suite. Include near-circular, eccentric, deep-space, invalid TLE,
coordinate conversion, range-rate and Doppler-sign tests. Until then, automated
pass tuning is experimental, not an accepted tracking solution.

Reference and vectors: [Vallado/CelesTrak AIAA 2006-6753](https://celestrak.org/publications/AIAA/2006-6753/).
Local reproduction: `build-audit-20260924/sgp4_audit.cpp` and `sgp4-audit.txt`.

### A05 / P1 - Inmarsat worker is guaranteed to fall behind 2.048 MS/s IQ

**Code-proven.** `src/InmarsatEngine.cpp:707` consumes at most 65,536 samples,
then `:788` sleeps 40 ms. Its absolute best throughput is 1.6384 MS/s before
any processing, below a normal 2.048 MS/s input. More CPU alone cannot fix that
scheduling limit. The half-ring catch-up pattern produces recurring backlog.

The latest 0.2.88 log contains repeated ring-overrun warnings, often about
42 seconds apart. This is consistent with this deficit, but the generic log
does not identify its consumer, so attribution of every warning to Inmarsat
would be an assumption. HF also has a confirmed throughput problem.

Repair: drain chronological input according to available samples/work budget,
separate UI refresh cadence from DSP consumption, propagate discontinuities,
and report reader identity, producer rate, consumer rate and lag. Test long
runs above the maximum advertised rate with injected worker stalls.

### A06 / P1 - Failed hardware tuning can be reported as successfully applied

**Code-proven.** `src/DeviceManager.cpp:2737` stores requested center frequency
before hardware application. At `:3049-3052`, exception paths still advance the
applied sequence. Inmarsat's confirmation at `src/InmarsatEngine.cpp:321` and
the analogous Satcom path combine that sequence with the cached requested
frequency. A rejected tune can consequently look successful.

Repair: separate requested, applied and failed tune results; advance success
only after driver acceptance, retain the last applied frequency on error, and
use hardware readback where available. Return a structured failure to GUI/CLI/
control DLL. Add fake-driver reject/clamp/timeout/out-of-order tests. This shared
change needs P25 non-regression coverage even though P25 DSP must not change.

### A07 / P1 - Follow metadata lookup lacks radio-system isolation

**Code-proven conditional bug; not established as the cause of this user's
recent follows.** `src/P25TalkgroupRegistry.cpp:793-833` selects a candidate
using TGID, freshness and optional channel/frequency, without checking control
channel or known WACN/System ID. It then copies NAC/WACN/System, slot, RID and
possibly encryption metadata at `:866-901`. A second system with the same TGID
can satisfy the filters, especially while channel/frequency is unresolved.
The function is called by GUI follow preparation, CLI and voice-test paths.

`p25TalkgroupStatusLabel` at `:1192-1230` also infers identity from another same-
TGID registry entry when identity is missing. That can produce a wrong alpha
tag even when the alias resolver itself correctly rejects ambiguity.

Repair: stable system/site/control-source identity before metadata enrichment;
unknown identity must not be filled from an ambiguous global TGID match.
Test two systems sharing TGID/channel numbers, missing metadata, stale rows,
and encrypted/clear conflicts. Limit changes to metadata matching, not vocoder,
TDMA, playout, masks, grace periods or encryption-release predicates.

### A08 / P1 - Direct sampling is not hardware-capability complete

**Code-proven scope/range issue; physical-device acceptance still required.**
`src/DeviceManager.cpp:114-123` substitutes fixed RTL ranges (500 kHz-28.8 MHz
with direct sampling; 24-1766 MHz without it). That loses the actual driver's
tuner/model coverage. RTL-SDR Blog V4 uses its native HF path, not direct
sampling; other RTL boards need the appropriate physical direct-sampling path.
The current generic RTL policy does not distinguish those cases.

`setDirectSampling` at `:1685-1729` persists the requested mode before confirmed
application, retunes RX channel zero, and does not establish a new stream epoch.
The primary GUI/control paths select device index zero rather than the active
selected device. Unsupported setting keys are tried without capability/readback
confirmation. The API can acknowledge an unsupported request as successful.

Repair: per-device/model capability and tune-range reporting, explicit supported
I/Q/off/native-HF modes, selected RX-channel routing and transactional live
mode changes with provenance reset. Preserve RSP/native-HF tuning ranges; do not
apply RTL direct-sampling rules to devices that do not require them. Test V3,
V4, generic tuner variants, RSP, non-RTL and unsupported-driver cases separately.

Primary hardware reference: [RTL-SDR Blog V4 guide](https://www.rtl-sdr.com/V4/).
Its updated driver and no-direct-sampling HF requirements are not interchangeable
with [the direct-sampling hardware guide](https://www.rtl-sdr.com/rtl-sdr-direct-sampling-mode/).

### A09 / P1 - Satellite Doppler retunes terminate live SSTV continuity

**Code-proven.** `src/SatcomScannerEngine.cpp:1189-1201` changes `lockHz_` and
hardware center once Doppler differs by 50 Hz. Processing resets demod/input
state on a tune gap and publishes `lockFrequencyHz` as decoder target identity
at `:1336`. `src/SstvStreamWorker.cpp:78-94` correctly rejects a gap or any
changed target frequency during one image. Normal pass tracking therefore
violates the streaming decoder's identity/continuity contract.

Repair: stable nominal downlink identity, continuous digital frequency tracking
inside a suitable hardware passband, and explicit retune/reacquisition boundaries
when hardware movement is unavoidable. Test a full image under a Doppler ramp
and actual loss/reacquisition; never silently splice discontinuous images.

### A10 / P2 - Scanner can lock outside its requested scan range and stay there

**Code-proven.** `src/SatcomScannerEngine.cpp:1218-1229` picks the strongest bin
across the full FFT, not just the requested scan/detection interval. At
`:1497-1512` it tunes to that peak. Once locked, `:1460-1475` only returns to
scanning on explicit Skip; it has no loss-of-signal unlock transition.

Repair: intersect detection with requested bounds and usable passband; define
validated acquire/release criteria, hysteresis and recording-tail policy.
Test a stronger out-of-range station plus a weak in-range target, then loss.

### A11 / P2 - Satellite data decoders receive speech-shaped audio

**Code-proven integration issue; end-to-end impairment not yet measured.**
`src/SatcomScannerEngine.cpp:1331-1362` requests a 3 kHz speaker LPF and sends
speaker-path audio to AX.25 and APT. Only SSTV receives the clean decoder tap.
Speech de-emphasis/filtering is not a neutral data path; it changes APRS tone
balance and suppresses APT subcarrier sidebands. Existing decoder smoke tests
feed clean synthetic decoder input and do not exercise this integration.

Repair: independent, rate-labelled pre-speech decoder taps with protocol-specific
channel filters; leave volume/de-emphasis/squelch in the listening branch.
Verify full IQ-to-packet/image chains with independent recorded fixtures and
arbitrary input partitions, not only decoder-local generated samples.

### A12 / P2 - Live SSTV UI advertises more than the worker accepts

**Code-proven.** `src/SstvStreamWorker.cpp:30` accepts only Auto/Robot36/Martin1.
The mode list exposes many additional modes which fail when selected for live
input. Main-window live attachment at `src/MainWindow.cpp:10765` remains NFM-
only despite the newer HF tap support elsewhere. PR #32 attempts HF GUI wiring
but does not remove the worker's explicit-mode restriction.

Repair: one shared capability source for file/live/GUI/CLI modes; qualify each
implemented streaming family and expose only qualified choices. Separate this
UI repair from PR #32's rejected decimation change. Independent off-air HF/SSTV
acceptance is still outstanding; local round trips are insufficient proof.

### A13 / P2 - HamDRM preview protocol is incompatible with the GUI parser

**Code-proven.** `src/sstv_backend/src/main.rs:303-317` emits final HamDRM image
metadata without progressive row events. `src/SstvImageFile.cpp:94-105` enables
progress when a preview callback exists. `src/SstvProgress.cpp:24-43` requires
the preceding rows and otherwise raises `SSTV preview completion mismatch`.
Auto's HamDRM file fallback has the same final-only output. Explicit live
HamDRM is also not an implemented stdin path.

Repair: version the helper's supported transport modes; either emit validated
row events or use a validated final-image path for this backend. Test through
the actual GUI wrapper, not only helper selftest.

### A14 / P2 - HamDRM is a private prototype, with integrity/size gaps

**Code-proven and gap.** `src/sstv_backend/src/hamdrm.rs` uses private STWN RGB
payloads, not EasyPal-compatible file transport. The computed FAC CRC is
discarded at `:228`. Encoding can stop at its 120-second cap and return success
before the payload is complete (`:179`). Receive payload dimensions and
multiplication need checked bounds before reconstruction (`:236-238`); the
outer helper checks dimensions only after decode. Current fixed-grid acquisition
also needs arbitrary-start/CFO qualification, not self-aligned round trips.

Repair: describe the prototype accurately, enforce integrity/checked arithmetic
and explicit truncation errors, and require external interoperability fixtures
before advertising standards-compatible digital SSTV. Keep helper isolation and
resource limits. Passing its 32x32 selftest does not demonstrate EasyPal support.

### A15 / P2 - Import rendering adds avoidable GUI-thread work

**Measured cost; runtime follow impact remains a risk.** The installed alias DB
contains 2,237 talkgroups; 100 repeated in-memory JSON parses averaged 7.10 ms
each on this host, excluding disk I/O and widgets. `populateP25TalkgroupTable`
at `src/P25TalkgroupRegistry.cpp:1233-1275` reloads the DB and recreates cells on
refresh. `src/MainWindow.cpp:1214`, `:5385`, `:5866` refresh during normal
control activity. This is not proof of the user's follow failure, but makes
GUI scheduling dependent on import size and event rate.

Manual Follow (`src/MainWindow.cpp:4471-4479`) also uses the selected visual row
as an index into a newly loaded disk list. It should bind to a stable identity,
not a row number whose backing file may have changed. Registry persistence
uses non-atomic truncating writes, unlike the safer alias-file save path.

Repair: immutable in-memory registry/alias snapshots, versioned cache invalidation,
coalesced/diff-based table updates, stable row keys, atomic persistence. Measure
event-loop latency with large imports and bursty grants before claiming a fix.

### A16 / P2 - HF output resampling depends on individual block boundaries

**Code-proven structure; audible contribution needs measurement.**
`src/HfDemod.cpp:279-299` stretches each block to a requested sample count with
endpoint interpolation, independently of previous output phase. The GUI supplies
rounded per-block counts (`src/MainWindowP25Orchestration.cpp:948-950`), whereas
the isolated HF test path uses natural output lengths. Uneven IQ partitions or
different output rates can therefore change the reconstructed waveform/cadence.

Repair: one persistent sample-clock conversion with explicit sample counts and
fractional remainder. Test whole-vs-irregular-partition waveform equivalence,
48/44.1 kHz outputs, startup, gaps and long-duration drift through the GUI path.

### A17 / P2 - Receiver ownership is not consistently per device or consumer

**Code-proven architecture limitation; concurrency scenarios require tests.**
The lease in `src/DeviceManager.cpp:1780-1835` is one global owner/device pair,
not one lease per physical device. Independent receivers can block one another.
Forced retunes need ownership-generation checks so stale workers cannot reclaim
a tuner after transfer. Inmarsat does not use the main-window takeover service
used by Satcom; ordinary Listen processing may continue on repurposed IQ.
`src/InmarsatWidget.cpp:275` calls synchronous start from the UI; its device and
tune waits can block the event loop on slow/failing hardware.

Repair: per-device leases with generation tokens, explicit consumer pause/restore,
asynchronous startup/teardown, and tests for simultaneous devices, preemption,
failed start, cancellation and shutdown. Do not broaden DSP changes to P25.
